## 二、優先處理（P0／P1）

### P0-1　更新簽章檢查沒有驗證檔案內容（高）
- 位置：`src/GpsTrackerPc.Core/Updates/UpdateInstallChecks.cs:61-80`
- 問題：
  - `X509Certificate.CreateFromSignedFile` 只會取出憑證，不會驗證 Authenticode 雜湊是否和檔案內容相符。
  - `chain.Build` 只檢查憑證鏈，沒有檢查「程式碼簽署」用途，也沒有比對簽署者是誰。
  - 竄改過的已簽章 EXE 仍會判為「受信任」。
- 影響：
  - 目前真正有效的防線只剩 SHA-256。
  - 檢查碼和 EXE 放在同一個 Release，能控制 Release 的人可以兩個一起換，所以沒有任何供應鏈保護。
- 建議（二選一）：
  1. 改用 `WinVerifyTrust`（`WINTRUST_ACTION_GENERIC_VERIFY_V2`），並固定（pin）憑證指紋。
  2. 沒有程式碼簽章憑證時：在 App 內嵌一把 Ed25519／ECDSA 公鑰，Release 另外附 `GpsTrackerPc.exe.sig`，安裝前用公鑰驗證。私鑰在離線環境簽署，不放在 CI。

```csharp
// 方案 2 示意（.NET 9 ECDsa）
using var ecdsa = ECDsa.Create();
ecdsa.ImportSubjectPublicKeyInfo(EmbeddedPublicKey, out _);
var ok = ecdsa.VerifyData(File.ReadAllBytes(exePath), signatureBytes, HashAlgorithmName.SHA256);
if (!ok) return UpdateApplyResult.Fail("更新檔簽章不符");
```

### P0-2　發佈流程先改 Release 標題、後上傳檔案（中高）
- 位置：`.github/workflows/desktop-release.yml:185-202`
- 問題：先執行 `gh release edit --title v新版`，之後才用 `--clobber` 上傳 EXE 和 `.sha256`。
- 影響：
  - 這段期間來檢查更新的用戶端，會看到新版號，卻下載到舊的 EXE 和舊的檢查碼（兩者雜湊相符），於是把舊版當成新版安裝。
  - 上傳中途失敗時，Release 會停在不一致的狀態。
- 建議：先上傳資產，最後才改標題和說明。更好的做法是每個版本建立自己的 `vX.Y.Z` Release，全部完成後再更新 `latest` 指標。

### P1-1　`.old` 回滾檔可能在更新後第一次啟動就被刪掉（中）
- 位置：`UpdateInstaller.cs:40`、`:76-77`
- 問題：`File.Move` 會保留原檔的 LastWriteTime，所以 `.old` 記到的是「上一次安裝」的時間，不是這次被換下來的時間。
- 影響：兩次更新相隔超過 7 天時，下次啟動就會刪掉 `.old`，「回復上一個版本」也就不能用。
- 建議：Move 之後補一行 `File.SetLastWriteTimeUtc(backupPath, DateTime.UtcNow);`

### P1-2　新版損壞時沒有自動回滾（中）
- 位置：`UpdateInstaller.cs:57-65`；呼叫端 `MainWindow.xaml.cs:1014`、`UpdateWindow.xaml.cs:206` 傳入的 `restart` 是 `() => {}`
- 影響：新 EXE 一啟動就崩潰時，使用者進不了程式，也就無法按「回復」。
- 建議：
  - 安裝時寫入「待確認」標記，首頁成功載入後才清掉。
  - 連續 2 次啟動失敗時，自動把 `.old` 換回來。

### P1-3　JSON 設定檔損毀時會被空清單覆蓋，造成資料遺失（中）
- 位置：`Util/AtomicFile.cs:22-23`、`FavoritesStore.cs:272/293`、`GpxFileHistoryStore.cs:204/219` 等所有 Store
- 問題：
  - `AtomicFile` 寫入後沒有呼叫 `Flush(true)` 就改名，斷電時可能留下 0 位元組的檔案。
  - Load 遇到 `JsonException` 時默默回傳空清單。
  - 下一次 Save 就用空清單（或只剩一筆）覆蓋原檔，例如收藏地點會全部遺失。
- 建議：抽出共用的 `JsonFileStore<T>` 基底類別，統一做這幾件事：
  - 用 `FileStream` 寫入並呼叫 `Flush(true)`，或改用 `File.Replace` 並保留 `.bak`。
  - 讀取失敗時先把壞檔改名成 `*.corrupt-<時間>`，並禁止用預設值覆蓋。
  - 反序列化逐筆容錯，一筆壞資料不影響整份清單。
  - 加一把鎖，因為 UI 執行緒和背景計時器會同時讀寫。

### P1-4　待上傳佇列會被一筆壞紀錄卡死（中）
- 位置：`PendingRecordUploader.cs:277-282`、`GitHubRecordUploader.cs:152`
- 問題：任何一筆失敗都會 `break`。佇列依建立時間排序，所以每 5 分鐘都卡在同一筆，後面的紀錄永遠傳不上去。
- 建議：
  - 失敗要分成暫時性（網路、401、速率限制）和永久性（422 驗證錯誤、格式錯誤）。只有暫時性錯誤才 `break`；永久性錯誤跳過這筆，`Attempts` 超過門檻就移到隔離區。
  - `GetValue<string>` 改用 `TryGetValue`。

### P1-5　GitHub 上傳不是原子操作，也沒有處理速率限制（中）
- 位置：`GitHubRecordUploader.cs:118-169`、`:348/400/525`
- 問題：
  - 流程是先 PUT 紀錄檔，再改 manifest，最後改 meta。合併時判定重複、manifest 衝突 3 次後放棄、或中途取消，都會在公開 repo 留下沒有被 manifest 引用的孤兒檔。GPX 每次重試都會產生新的 GUID，孤兒檔會一直累積。
  - 遇到 403／429 一律直接失敗，沒有看 `Retry-After` 和 `x-ratelimit-reset`。批次匯入上百筆時，碰到次要速率限制後整批都會失敗。
  - 422 被一律當成衝突重試。
- 建議：
  - 改用 Git Data API（blob → tree → commit → 帶舊 sha 更新 ref），一次 commit 寫入所有檔案。
  - 抽出共用的 `GitHubClient`，統一處理 Retry-After、指數退避加 jitter、錯誤分類。
  - 批次匯入遇到速率限制時暫停，不要繼續打 API。

### P1-6　WebView2 導航與資料夾對映範圍過大（中）
- 位置：`MainWindow.xaml.cs:221-224`；`FriendsView.xaml.cs:171-176`；`SimulatorView.xaml.cs:349-356、384-489`
- 問題：
  - `gpstracker-data.local` 用 `Allow` 對映整個資料夾。如果使用者把資料夾設成 `%LOCALAPPDATA%\GpsTrackerPc` 或家目錄，`social.json` 等檔案都能從網頁讀到。
  - 三個 WebView 都沒有 `NavigationStarting` 白名單；Simulator 和 Friends 也沒有攔截 `NewWindowRequested`（MapLibre 署名連結是 `target=_blank`）。
  - `WebMessageReceived` 沒有驗證 `e.Source`。根節點不是物件時會丟 `InvalidOperationException`，但程式只接 `JsonException`。
- 建議：抽出共用的 `WebViewHost.InitializeAsync(allowedOrigin)`，在一處集中處理：
  - `NavigationStarting` 只放行自己的 origin，其他網址交給系統瀏覽器。
  - 攔截 `NewWindowRequested`。
  - 訂閱 `ProcessFailed`，失敗時停止播放並提示使用者。
  - 驗證訊息的 `Source` 和 `ValueKind == Object`。
  - 對映改成 `DenyCors`；資料夾設定要拒絕程式根目錄、磁碟根目錄和家目錄。

### P1-7　接續播放在「多點短圈」路線會失敗（中）
- 位置：`PlaybackController.cs:152`、`RouteSimulator.cs:23`（`MaxAdvanceIterations = 10_000`）
- 問題：還原時每次往前推 600 秒，循環路線每經過一個點就算一次迴圈。
- 例子：500 點、一圈約 11 秒的環狀路線，600 秒約 2.7 萬次迴圈，超過上限就丟 `InvalidOperationException`，「從暫停點繼續」因此失敗。
- 建議：把步長改成不超過一圈的時間（或 1 秒），並補一個「多點、短圈、圈數多」的還原測試。

## 三、中低優先（P2）

### 安全與隱私
1. **好友分享金鑰以明文存放**（`SocialSettingsStore.cs:167-171`）：`KeyBase64` 等同可長期讀取好友位置的權杖，建議用既有的 DPAPI `ISecretProtector` 加密。
2. **邀請碼可以指定任意中繼伺服器**（`SocialValidation.cs:276-290`）：
   - 可指定 http 或內網位址，形成類似 SSRF 的情況。
   - `PollAsync` 沒有限制單行長度，錯誤回應讀取也沒有大小上限，惡意伺服器可以把記憶體吃光。
   - 建議：只接受 https、拒絕私有和 loopback 位址，讀取時套用 `BoundedIo.Limit`。
3. **群組成員可以互相冒充，而且無法撤銷**（`SocialCrypto.cs:16/90`、`SocialPresence.cs:384`）：
   - 群組共用一把對稱金鑰，AAD 沒有綁定 DeviceId。
   - 移除好友只刪本機資料，沒有換金鑰的機制。
   - 時間戳記容許比現在晚 10 分鐘。
   - 建議：提供「重新產生金鑰」功能，payload 加 epoch 欄位，未來時間容許範圍縮到 1 分鐘。長期可改成每台裝置用自己的 Ed25519 金鑰簽署。
4. **驗證與安裝之間有時間差（TOCTOU）**（`MainWindow.xaml.cs:800/971`）：檔案已存在時會跳過下載和雜湊檢查，安裝前也沒有重算。建議在 `Apply` 前重新驗證 SHA-256。
5. **Range 續傳沒有送 `If-Range`**（`UpdateService.cs:478-496`）：Release 被覆蓋後會把新舊內容接在一起。SHA-256 會擋下來，但要整份重新下載。
6. **檢查碼檔只取第一個 64 位十六進位字串**（`UpdateService.cs:587`），沒有比對檔名欄位。

### 正確性與穩定性
7. **更新或回復重啟時跳過清理**（`MainWindow.xaml.cs:1099/1172` 配合 `1480`）：這兩個流程先設 `_closing=true` 才 Shutdown，所以系統匣圖示、計時器、NetworkChange 事件、HttpClient 都沒有釋放。建議抽出 `Cleanup()`，兩條路徑都呼叫。
8. **crash.log 沒有節流也沒有大小上限**（`App.xaml.cs:110-167`）：`SimulatorView:684` 的 `Post` 沒有包 try。WebView2 程序掛掉後每 500 ms 會寫一次 log。建議加大小輪替，同一個例外短時間內只記一次。
9. **單一實例 Mutex**（`App.xaml.cs:77`）：沒有接住 `AbandonedMutexException`。第二個實例只跳訊息，沒有把已開啟的視窗叫到前面（主視窗縮在系統匣時特別不好找）。
10. **同步遇到單一檔案被鎖住就中斷整次**（`DataSyncService.cs:145/187`）：防毒軟體或 WebView2 鎖住檔案時，後面的檔案都不會下載。建議在單檔層級接 IOException，並對 `File.Move` 短暫重試。
11. **自動補傳與手動補傳可以同時執行**（`MainWindow:1322` 和 `PendingRecordsWindow:60` 是兩個獨立的旗標）：建議改成同一個 `SemaphoreSlim`。關閉視窗時也要傳入 CancellationToken。
12. **haversine 在接近對蹠點時會算出 NaN**（`GeoMath.cs:16-19`）：建議 `a = Math.Clamp(a, 0, 1)`。
13. **GPX 解析的邊界情況**（`GpxTrackBuilder.cs`）：
    - `<name>` 裡的 CDATA 會被遮成空白，標題因此遺失。
    - `<trk>` 沒有 name 時，會抓到 `<trkpt>` 裡的 name。
    - `&#x..;` 數字實體不會被解碼。
    - 100 MB 的檔案峰值記憶體可能超過 500 MB。
    - 長期建議改用 `XmlReader` 串流解析，Simulation 端的 `GpxStreamImporter` 已有類似做法，可以共用。
14. **每日上限的日期字串沒有指定文化**（`PendingRecordUploader.cs:367`）：在泰文等使用佛曆的文化下，年份會不同。建議加上 `CultureInfo.InvariantCulture`。
15. **Nominatim 的 User-Agent**（`NominatimGeocoder.cs:512`）：`GpsTrackerPc/1.0` 沒有附聯絡方式，不符合 OSM 使用政策的建議。也沒有快取查詢結果。
16. **隨機路線沒有記錄種子**（`SimulatorView.xaml.cs:1122`）：使用者回報問題時無法重現同一條路線。

### 4.2 CI／建置
1. **新增 `ci.yml`**：在 `pull_request` 和 `push: main` 時執行下列項目。目前測試只在推 tag 發佈時才跑，JS 測試完全沒有進 CI。
   - `dotnet test --collect:"XPlat Code Coverage"`
   - `node --test tests/js/*.test.js`
2. **發佈 workflow 加強**：
   - 權限只給發佈那一步，其他預設 `contents: read`。
   - actions 改成鎖定 commit SHA。
   - `ANDROID-APP-DEV` checkout 指定 `ref`（固定 commit 或 tag），讓打包內容可以重現。
   - `workflow_dispatch` 限制只能從 main 執行。
3. **新增 `Directory.Build.props`**：`TreatWarningsAsErrors`、`AnalysisLevel=latest-recommended`、`EnforceCodeStyleInBuild`、`RestorePackagesWithLockFile`。
4. **新增 `global.json`**（固定 SDK 9.0.x patch 版本）和 `.editorconfig`。
5. **縮小發佈檔**（目前單檔 EXE 約 200 MB）：
   - `-p:EnableCompressionInSingleFile=true`：通常能縮小 40-50%，代價是啟動時要多解壓一次。
   - `-p:SatelliteResourceLanguages=zh-Hant;en`：去掉 WPF 的多語系資源。
   - WPF 不支援 trimming，不要開啟。
6. **套件更新**：WebView2 4258 → 4314、`System.Security.Cryptography.ProtectedData` 升到最新 9.0.x。

### 4.3 測試缺口
- 完全沒有測試的類別：`AtomicFile`、`SyncFileCache`、`NetworkCostHeuristic`、`CurrentLocationProvider`、`ModeCatalog`、`AppVersion`、`Coordinates.Parse`
- 建議補上：
  - `AtomicFile` 與各 Store 的壞檔復原（配合 P1-3）
  - 在 `de-DE`／`th-TH` 文化設定下，RouteJsonCodec 和 LocationDocumentCodec 存回讀出結果一致
  - P1-7 的還原迴圈測試
  - 待上傳佇列遇到永久性錯誤時會跳過（P1-4）
- JS 測試加一個 `package.json`，內含 `"test": "node --test tests/js/*.test.js"`

### 4.4 Repo 整理
- 根目錄有 `全部程式碼.txt`（1 MB）和 `GpsTrackerPc-win-x64.zip.sha256`，都沒有被版控，也不在 `.gitignore` 裡，很容易被 `git add .` 誤加。建議 `.gitignore` 加上 `*.sha256` 和 `全部程式碼.txt`。
- `GpsTrackerPc-win-x64/`（494 MB）是本機測試資料夾，裡面有：
  - `GpsTrackerPc.exe.WebView2`（85 MB 的 WebView2 使用者資料：Cookie、快取）
  - `GpsTrackerPc.exe.old`
  - `data/` 同步資料
  
  這個資料夾**不要直接壓縮分享**。建議本機測試改在 repo 外的目錄執行。
- `.kilo/` 是空資料夾，可以刪除。
